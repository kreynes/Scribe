# How are locks scoped by branch, and how do sync conflicts surface?

Research for issue #16. All claims are from the Lore source at tag `v0.10.1` (commit `95a9a834f184`, the latest release as of 2026-10-15). `main` is 94 commits ahead of that tag; I did not read `main`, so anything below could have changed there. Nothing was run against a live `loreserver`; every claim is from reading code. Claims I could not verify in code are marked **Guess**.

All links point at `https://github.com/EpicGames/lore/blob/v0.10.1/...`.

## Short answers

1. A lock belongs to a (repository, branch id, path) triple. Locks on different branches are independent, even for the same path: two people can hold the same path on two branches. A lock on `main` does nothing to someone on another branch as far as the lock store is concerned.
2. When `--branch` is omitted, acquire, status and release use the **currently checked-out branch** of the working copy. They do not default to `main` or to the repository default branch. `query` is different: omitting `--branch` means "all branches".
3. `lock query` with no filters lists every lock in the repository across all branches, so a "who is editing what" board is possible. Each result carries a branch **id**, not a name. The owner is the server's user id string; `--owner` on the CLI takes a user **name** and resolves it to an id.
4. Admin release needs no special CLI flag. The server skips the ownership check when the caller has the `owner` or `admin` permission on the repository. Admin acquire-on-behalf (`file_acquire_as_owner`) needs the `migrate` permission and is not exposed by the CLI.
5. `revision sync` over locally modified files does not report conflicts and does not auto-merge. If an incoming change touches a file with uncommitted local edits, the whole sync fails with a `LocalModifications` error before any file is written. `--forward-changes` keeps the local edits and skips those files; `--reset` overwrites them with the incoming content. The `branch merge ... resolve mine/theirs` machinery is only used when committed local history has diverged from the remote, and then it is a staged merge with conflicts.

## 1. What a lock's branch means

- A lock's identity is `(repository, branch, hash-of-path)`. The in-memory server lock store keys on exactly these three fields: [`lore-server/src/lock/store.rs` L16-L21](https://github.com/EpicGames/lore/blob/v0.10.1/lore-server/src/lock/store.rs#L16-L21). `lock_resources` inserts per key and fails only when the same key is held by a different owner (the same owner re-acquiring is a no-op): [L39-L72](https://github.com/EpicGames/lore/blob/v0.10.1/lore-server/src/lock/store.rs#L39-L72). The path hash is a hash of the repo-relative path string: [`lore-revision/src/lock/util.rs` L9-L17](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/util.rs#L9-L17).
- Consequence, directly from the key: the same path locked on `main` by Alice and on `feature` by Bob are two separate entries and both succeed. There is no inheritance from parent to child branch and no cross-branch exclusion in the lock store. (The DynamoDB store in `lore-aws` is the production backend; I did not read it. **Guess:** it keys the same way, since it implements the same `LockStore` trait with the same arguments: [`lore-revision/src/lock.rs` L40-L70](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock.rs#L40-L70).)
- Default branch when `--branch` is omitted:
  - acquire: [`acquire.rs` L133-L141](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/acquire.rs#L133-L141), the branch from `load_current_anchor`, i.e. the branch the working copy is on.
  - release: [`release.rs` L137-L145](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/release.rs#L137-L145), same.
  - status: [`status.rs` L138-L144](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/status.rs#L138-L144), same.
  - query: [`query.rs` L90-L97](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/query.rs#L90-L97), empty means `None`, i.e. every branch.
  - The CLI passes the flag straight through as an optional string: [`lore-client/src/cli/commands/lock.rs` L51-L96](https://github.com/EpicGames/lore/blob/v0.10.1/lore-client/src/cli/commands/lock.rs#L51-L96). A non-empty `--branch` is resolved by name through `branch::resolve` to a branch id.
- Does a lock on `main` affect someone editing on another branch? In the lock store, no. Whether the server refuses a push that touches a file locked by someone else is a separate question. The design doc says it does ("an attempt by another client to push a change to a locked file is rejected by the server": [`docs/explanation/system-design.md` L1443-L1446](https://github.com/EpicGames/lore/blob/v0.10.1/docs/explanation/system-design.md#L1443-L1446)), while the approved lock proposal calls the current primitive "opt-in compliance" ([`docs/proposals/2026-06-19-successor-locks-unmergeable-files.md`](https://github.com/EpicGames/lore/blob/v0.10.1/docs/proposals/2026-06-19-successor-locks-unmergeable-files.md), Motivation and Goal 8). I searched `lore-server/src`, `lore-revision/src/branch` and `commit.rs` for any lock check on the push or commit path and found none. **Guess:** at `v0.10.1` locks are advisory, with enforcement not present in the public code. Worth confirming with an actual push in a spike (it belongs with #13).
- Two other things that proposal says, relevant to the prototype: locks are "released on commit or push" today (overlaps #13), and a future "scope" system would make cross-branch causality explicit. Both are proposal text, not something I verified in code.
- Local `loreserver` caveat: the `local` lock store is an in-process in-memory map, so locks vanish when the server restarts and only coordinate within one node: [`docs/reference/lore-server-config.md` L465](https://github.com/EpicGames/lore/blob/v0.10.1/docs/reference/lore-server-config.md#L465).
- Locking needs a remote: acquire, release, status and query all fail with an "offline" error if no remote is reachable (for example [`acquire.rs` L195-L199](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/acquire.rs#L195-L199)).

### Implication for UI
- "Locked on `<branch>`" is accurate and necessary: the same path can show up several times with different branches.
- "main as the default" is **not** accurate. The default is the working copy's current branch. If Scribe always passes an explicit branch it avoids ambiguity. Without it, a user on a feature branch locking a file locks it on the feature branch only.

## 2. `lock query` and owner ids

- Server query combinations accepted: none, branch, branch+path, owner, owner+branch. Anything else is `InvalidArguments` ("unsupported lock query combination"): [`lore-server/src/grpc/lock_service.rs` L45-L73](https://github.com/EpicGames/lore/blob/v0.10.1/lore-server/src/grpc/lock_service.rs#L45-L73). So `(None, None, None)` returns every lock in the repository, which is the "who is editing what" board query. Note that `--path` **without** `--branch` is rejected, and `--path` together with `--owner` is rejected.
- Event shape: `LockFileQueryBegin { count }` then one `LockFileQuery { branch: BranchId, path, owner, locked_at }` per lock: type at [`query.rs` L50-L69](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/query.rs#L50-L69), emission at [L141-L160](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/query.rs#L141-L160). `locked_at` is milliseconds since the Unix epoch (the CLI feeds it to `DateTime::from_timestamp_millis`: [`lock.rs` L299-L303](https://github.com/EpicGames/lore/blob/v0.10.1/lore-client/src/cli/commands/lock.rs#L299-L303)). The branch is an id; to show a name the CLI maps ids through a branch-name resolver ([`branch.rs` L680](https://github.com/EpicGames/lore/blob/v0.10.1/lore-client/src/cli/commands/branch.rs#L680)), so Scribe needs a branch list lookup too.
- Owner format: the lock's `owner` is `token.identity()` from the caller's auth token ([`lore-server/src/util/mod.rs` L36-L42](https://github.com/EpicGames/lore/blob/v0.10.1/lore-server/src/util/mod.rs#L36-L42)), or the literal `"<unknown>"` when there is no token. It is an opaque identity string whose exact shape depends on the auth provider (**Guess:** a subject/user id, not a display name). The CLI turns ids into display names with an extra `AuthUserInfo { id, name }` call: [`lock.rs` L305-L339](https://github.com/EpicGames/lore/blob/v0.10.1/lore-client/src/cli/commands/lock.rs#L305-L339).
- The CLI help says `--owner <owner-id>`, but the library resolves the value as a user **name** to an id before querying: [`query.rs` L99-L107](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/query.rs#L99-L107) via `auth::userinfo::user_id`. Release has a separate `owner_id` argument that skips this lookup (empty in the CLI, usable through the library API): [`release.rs` L146-L158](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/release.rs#L146-L158).
- `lock status` takes explicit paths (server limit 100 per request, client batches by 100: [`lock_service.rs` L40](https://github.com/EpicGames/lore/blob/v0.10.1/lore-server/src/grpc/lock_service.rs#L40), [`util.rs` L7](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/util.rs#L7)). Its event has no branch field: `LockFileStatus { path, owner, locked_at }`: [`status.rs` L109-L122](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/status.rs#L109-L122). Use `query` for a cross-branch board and `status` for "is this file I'm about to open locked on my branch".
- Live updates: the server sends `ResourceLocked` / `ResourceUnlocked` notifications on lock and unlock ([`lock_service.rs` L161-L163, L333-L337](https://github.com/EpicGames/lore/blob/v0.10.1/lore-server/src/grpc/lock_service.rs#L161-L163); [`notification/local.rs` L108-L146](https://github.com/EpicGames/lore/blob/v0.10.1/lore-server/src/notification/local.rs#L108-L146)). I did not trace how a client subscribes; a board could poll `lock query` instead.

## 3. Admin release and acquire-as-owner

- **Release of another user's lock.** `unlock` computes `validate_user = !is_elevated(...)`, and `is_elevated` is true when the caller has `owner` **or** `admin` on the repository: [`lock_service.rs` L170-L179, L297-L328](https://github.com/EpicGames/lore/blob/v0.10.1/lore-server/src/grpc/lock_service.rs#L170-L179). Without elevation, releasing someone else's lock fails with `LockNotOwned` (gRPC `FAILED_PRECONDITION`; message "resource locked by somebody else", ffi code 45: [`lore-base/src/error.rs` L236-L239](https://github.com/EpicGames/lore/blob/v0.10.1/lore-base/src/error.rs#L236-L239)). Server unit tests for this are in [`lore-server/tests/unit/grpc/lock_service.rs`](https://github.com/EpicGames/lore/blob/v0.10.1/lore-server/tests/unit/grpc/lock_service.rs) (I read the admin-lock tests at about L387-L450; the elevation tests sit just above).
- **What `release --owner` actually does.** The owner is only used when **no paths** are given together with `--force`: the client queries that owner's locks on the branch and releases all of them: [`release.rs` L208-L228](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/release.rs#L208-L228). With explicit paths the owner is resolved but then unused, and the `unlock` RPC carries no owner at all ([`release.rs` L278](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/release.rs#L278); [`lock_client.rs` L141-L170](https://github.com/EpicGames/lore/blob/v0.10.1/lore-transport/src/grpc/lock_client.rs#L141-L170)). So "admin release" means an `owner`/`admin` user releasing the given paths on the right branch; the server does the permission check, not the client.
- Releasing a lock that does not exist is not an error: the client turns gRPC `NotFound` into an empty result, and the CLI prints "Lock does not exist for requested files" ([`lock_client.rs` L155-L158](https://github.com/EpicGames/lore/blob/v0.10.1/lore-transport/src/grpc/lock_client.rs#L155-L158); `LockFileReleaseBegin { not_found }`: [`release.rs` L111-L114](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/lock/file/release.rs#L111-L114)).
- **Acquire on behalf of someone** (`file_acquire_as_owner`, a library function not wired to the CLI: [`lore/src/lock.rs` L80-L102](https://github.com/EpicGames/lore/blob/v0.10.1/lore/src/lock.rs#L80-L102)) sends an `AdminLockRequest`, which the server permits only with the `migrate` permission: [`lock_service.rs` L346-L385](https://github.com/EpicGames/lore/blob/v0.10.1/lore-server/src/grpc/lock_service.rs#L346-L385) (test `admin_lock_requires_migrate_on_both_tiers`). `migrate` looks meant for import tooling (**Guess**). Scribe should not need it.
- A request with no auth token is never elevated (test `no_token_means_no_elevation_and_no_admin_lock`), so on a no-auth local server you probably cannot release other users' locks, though every client is then the same `<unknown>` owner anyway (**Guess**; not run).
- The ordinary permission for acquiring and releasing your own locks: the tests use a token granting `push`. I did not find the interceptor that maps lock RPCs to permissions, so **Guess:** `push`.

## 4. What `revision sync` does with locally modified files

Two distinct paths, chosen in [`lore-revision/src/revision/sync.rs`](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/revision/sync.rs).

### 4a. Uncommitted local edits that the incoming revision also changes: refused, not merged
- A sync with **staged** (`lore stage`d) changes is rejected with `InvalidArguments` "Unable to sync when there is a staged state", unless `--force` or `--reset`: [`sync.rs` L463-L487](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/revision/sync.rs#L463-L487).
- Otherwise `realize_state` computes the delta current to target and, unless `--force`/`--reset`, runs `verify_filesystem_for_changes` over every change: [`lore-revision/src/fs/realize.rs` L236-L249](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/fs/realize.rs#L236-L249). For a file whose working-tree content differs from the incoming node, and is not content the change already accounts for, it logs "File has local changes: ..." and returns `LocalModifications`: [`realize.rs` L757-L792](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/fs/realize.rs#L757-L792). The same error covers "incoming deletes a file that is locally modified" ([L706-L718](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/fs/realize.rs#L706-L718)). The first failure aborts the verification phase ([`realize.rs` L283-L345](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/fs/realize.rs#L283-L345)) and `realize_changes` is never reached, so **nothing is written to the working tree**.
- What the caller sees: no per-file conflict event. It gets `LoreEvent::Error` ([`LoreErrorEventData { error_type, error_inner }`: `event.rs` L532-L537](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/event.rs#L532-L537)) and a `Complete` event with non-zero `status` and an `error` detail ([`event.rs` L552-L561](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/event.rs#L552-L561)). The error text is "Local modifications prevent synchronization" (ffi code 44: [`lore-base/src/error.rs` L231-L234](https://github.com/EpicGames/lore/blob/v0.10.1/lore-base/src/error.rs#L231-L234)); the offending paths appear only in log output ("File has local changes: <path> ..."). **Gap:** I found no structured event listing the blocking paths. To list them for the user, Scribe would run a status/diff call itself (or parse log events). **Guess:** `error_type` may read as the generic internal code, since for the lock errors `EventError::translated()` returns `LoreError::Internal`; I did not trace the sync error mapping, so the discriminating field is probably `Complete.error`.
- Files with local edits that the incoming revision does *not* touch are left alone (verification only covers files in the delta).
- Local edits that already equal the incoming content count as "nothing to do" (`NodeComparison::Matches`, [`realize.rs` L793-L817](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/fs/realize.rs#L793-L817)).

### 4b. `--forward-changes` and `--reset`
- `--forward-changes` ("Fast forward any local changes", [`lore-client/src/cli/commands/revision.rs` L199-L201](https://github.com/EpicGames/lore/blob/v0.10.1/lore-client/src/cli/commands/revision.rs#L199-L201)): in `verify_filesystem`, every case that would have been `LocalModifications` instead logs "Keeping modified file as locally modified" (or "Keeping deleted file as locally modified", "Keeping modified file as locally deleted") and drops that change, so the local file is left as is and the rest of the sync proceeds: [`realize.rs` L620-L629, L697-L722, L751-L756, L826-L833](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/fs/realize.rs#L620-L629). The anchor still moves to the target revision, so the kept file then shows as a local modification relative to the new revision. The skipped paths are logged, not emitted as events (**Guess**, from the absence of any event emission in those branches).
- `--reset` ("Reset any local modified files to match the incoming revision"; clap makes it conflict with `--forward-changes`: [`revision.rs` L203-L205](https://github.com/EpicGames/lore/blob/v0.10.1/lore-client/src/cli/commands/revision.rs#L203-L205)): diffs the **filesystem** against the target instead of the current revision, so every locally modified file is overwritten with the target's content, local edits are discarded, and verification is skipped: [`realize.rs` L133-L184, L236](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/fs/realize.rs#L133-L184). It also lets a sync proceed over staged changes ([`sync.rs` L469](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/revision/sync.rs#L469)) and a sync to the revision you are already on (L753). This is destructive; Scribe needs a confirm step. A reset does not touch locks.
- Global `--force` also skips the verification ([`realize.rs` L236](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/fs/realize.rs#L236)) and, for an implicit sync with diverged history, makes sync pick the remote and skip the merge ([`sync.rs` L581-L597](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/revision/sync.rs#L581-L597)). I did not work out all of its semantics; out of scope.

### 4c. Committed local revisions diverged from the remote: auto-merge, conflicts staged
- This path applies only to an **implicit** sync (no revision argument) that can reach the remote, where local latest and remote latest have each moved past their common ancestor and the working copy is not already ahead: [`sync.rs` L766-L845](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/revision/sync.rs#L766-L845), with target selection at [L559-L635](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/revision/sync.rs#L559-L635). An explicit revision argument "must not trigger divergence resolution" (code comment at L772-L773).
- It calls the same `branch::merge::merge_start` that `lore branch merge start` uses, with `no_commit: false`: [`sync.rs` L811-L826](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/revision/sync.rs#L811-L826). Per the doc comment on the public API ([`lore/src/revision.rs` L707-L727](https://github.com/EpicGames/lore/blob/v0.10.1/lore/src/revision.rs#L707-L727)) and the merge code, the events are:
  - `BranchMergeStartBegin { branch, revision, revision_number }` ([`merge.rs` L568-L573](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/branch/merge.rs#L568-L573)),
  - `BranchMergeStartEnd { stats, signature, has_conflicts }` ([`merge.rs` L624-L629](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/branch/merge.rs#L624-L629)),
  - one `BranchMergeConflictFile { path }` per conflicted file ([`merge.rs` L2620-L2636](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/branch/merge.rs#L2620-L2636)),
  - then `RevisionSyncRevision { branch, revision, revision_number, flag_merge, flag_conflict }`, where `flag_conflict` is set when the staged merge revision has conflicts and `revision_number` is 0 for a staged merge ([`sync.rs` L125-L134, L832-L843](https://github.com/EpicGames/lore/blob/v0.10.1/lore-revision/src/revision/sync.rs#L125-L134)). The `RevisionSyncProgress` stats also carry `file_automerge` and `file_conflict` counts (L103-L107).
  - With no conflicts the merge auto-commits and the `RevisionCommit*` events follow.
- The CLI's sync handler does **not** print `BranchMergeConflictFile` or `BranchMergeStart*` ([`revision.rs` L1426-L1495](https://github.com/EpicGames/lore/blob/v0.10.1/lore-client/src/cli/commands/revision.rs#L1426-L1495)); it only prints sync target and progress. A library consumer such as Scribe receives them directly.
- Resolution uses the normal merge machinery: `lore branch merge resolve [mine|theirs] <paths>`, `unresolve`, `abort`. Subcommands: [`lore-client/src/cli/commands/branch.rs` L224-L305, L361-L378](https://github.com/EpicGames/lore/blob/v0.10.1/lore-client/src/cli/commands/branch.rs#L361-L378); events `BranchMergeResolveFile { path }`, `BranchMergeUnresolveFile`, `BranchMergeAbortBegin/End`. Because the merge is *staged* in the working copy, this state also blocks the next sync ("Unable to sync when there is a staged state").
- Not verified: which side `mine`/`theirs` is in this sync-triggered case. I assumed the same orientation as `branch merge start` (current branch is mine). **Guess.**

## 5. Do the prototype's guesses hold?

| Prototype guess | Verdict |
|---|---|
| Show each lock "on `<branch>`" | Holds, and is needed: the same path can be locked separately on several branches. `query` returns a branch id, so Scribe must map id to name. |
| `main` is the default branch for locks | **Does not hold.** Default is the branch the working copy is on (acquire, status, release). `query` with no branch means all branches. Scribe should pass the branch explicitly. |
| Sync clashes are routed into the merge conflict screen using `lore branch merge resolve` | **Partly.** True only for diverged committed history (4c). For the common case of a file edited locally while the incoming revision changes it, sync fails whole with `LocalModifications` and there is nothing to resolve with mine/theirs; the options are keep local (`--forward-changes`), discard local (`--reset`), or commit first and sync again (which lands in 4c if the remote also moved). |

## 6. Implications for Scribe

- Locks board: one `lock query` with no filters, plus a branch id to name map and an owner id to name map (`AuthUserInfo`). Re-poll, or use the notification stream.
- Always pass the branch to lock calls. Check `lock status` on the current branch before opening a file, but be aware another branch can hold its own lock on the same path and Lore will not warn about it.
- A lock does not stop a sync from overwriting your local edits; they are separate systems. A locked, locally edited file that the incoming revision also changes still hits `LocalModifications`.
- A sync UI needs three outcomes: clean; blocked by local modifications (offer keep local / discard local / cancel; the paths must come from a status call because the error carries no path list); and diverged merge with conflicts (route to the merge screen).
- Follow-ups worth a spike against a local `loreserver`: (a) does push or commit enforce locks held by others, (b) what `Complete.error` contains for `LocalModifications` and whether the paths appear in any event, (c) the real shape of an owner id, (d) mine/theirs orientation in a sync-triggered merge.
